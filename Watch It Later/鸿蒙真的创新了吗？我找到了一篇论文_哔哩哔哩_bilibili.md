但我想知道抛开这些，仅从技术去理解鸿蒙到底做了什么。论文的标题是微内核走向通用内核操作系统中最基本的部分，它的真实样貌是始终驻留在内存中的一系列代码，时刻连接着软件与硬件，掌控着计算机中的一切进程调度、内存分配、文件管理、外接设备。女朋友发来微信网卡接收到数据，进入内核处理内核调度其他进程，将数据载入内存，最后微信弹出消息，进程就是执行中的程序，打开任务管理器，这就是你电脑中目前的进程。要顺利收到微信，涉及到一系列基础进程，都在任务管理器的系统服务一栏，它们是操作系统中最底层的进程，被叫做服务。服务分为两种，内核态与用户态服务。二者的区别在于权限用户态服务有限制，但内核态服务却可访问所有硬件资源，拥有最高权限，就像宿管阿姨可以随时出入寝室。一般来说，内核态服务组成操作系统的内核服务数量多叫宏内核，少则是微内核，二者数量界限没有硬性规定，甚至偶尔用户态服务也会被放进内核。完全看设计者的意思，比如这是 Linux 的内核架构，而这是鸿蒙内核中包含的服务代码量只有 Linux 宏内核的 1/ 1, 000，更少的 bug 更不容易受网络攻击，并且由于微内核将大量服务都扔在用户态服务之间解耦互不影响，增减服务方便，所以扩展性也更好。
就像中科大的孟宁所说，下一代操作系统主要面向万物互联。然而一查，现在的操作系统没有一个完全以微内核为基础设计，如果微内核真如说的那么好，为什么会没人用呢？我继续搜索才发现微内核曾经与宏内核并驾齐驱，甚至一度被认为是操作系统的未来，直到上世纪的一场网络骂战。彼时微软刚推出 Windows 3.0， Mac OS 还叫 system seven Linux 咕咕坠地发布还不到半年，微内核系统 Minix 作者 Tanenbaum 在技术论坛上发表了一篇帖子，标题是 Linux 已经过时。在 Tanenbaum 看来，宏内核简单粗暴的将所有服务都放进内核，远不如微内核安全稳定，而微内核性能不足的短板此时已被一款叫 Mac 3.0 的系统补齐。 Linus 竟然在这个时候选择写一个宏内核系统，仿佛 49 年入国军。因此 Tanenbaum 认为这场内核之争，微内核早已胜出。

我想知道微内核性能究竟有什么问题？微内核与宏内核设计上的根本区别在于微内核的服务更多在用户态，他们的地址空间独立，彼此隔离。当微信这个用户态进程要调取网卡缓存中的数据时，就要经过更高权限的内核中转，这一过程叫做进程间通信，就是一次IPC，就像你去女生宿舍找你女朋友，得经过宿管阿姨。
IPC 经过内核的这一步叫做陷入内核，这是最耗时的一步。陷入内核要涉及到保存上下文、加载内核进程参数验证耗时会达到 CPU 执行一条指令的几十到几百倍。如果服务进程都在内核态中，权限最高，可直接访问硬件资源，就像你拿到了宿管阿姨的钥匙。用户态进程之间通信一次往往需要 1, 000 多个 CPU 周期，而内核态仅需几个周期。
微内核的用户态服务远远多于宏内核， IPC 频繁、耗时惊人，这正是微内核的死穴。在内核之争发生的 90 年代， IPC 已经成为微内核的阿喀琉斯之踵，于是大家逐渐又把服务放回内核里去了。一些人甚至对微内核完全失去信心，认为 IPC 损耗是微内核不可能克服的固有缺陷，彻底摧毁人们信心的一击来自那个蓝色巨人 workplace OS，一个被 IBM 寄予厚望的微内核系统。

从此， IBM 彻底退出 PC 历史舞台。加州大学的一篇案例研究将这次微内核系统的押注成为现代操作系统最大失败之一。几乎就在同一时期，在大西洋的另一端，微内核尚存一息。 1993 年，德国国家计算机研究中心的 Ledics 宣称他设计的微内核系统 IPC 耗时被压缩到了 5 微秒，当时普遍的时间是 100 微秒，降低了足足 20 倍。他在论文中提出了一共 18 种优化方案，但思路无非两种，要么减少 IPC 的次数，要么降低单次 IPC 的时间开销。
let it go 首先解除了对一次通信长度的限制，这样一次 IPC 就能有更多数据，次数就降低了，它称之为复杂消息。而单次 IPC 的时间都浪费在了陷入内核，这本质上是因为用户态进程的权限不够，只能通过更高权限的内核中转数据。 let it go，利用操作系统一个机制来偷机虚拟内存。操作系统给每个进程分配了一张空白连续地址，这就是虚拟内存进程，只管把数据存进去，并不知道具体数据在哪，系统将这些信息都保存在一张页表中，上面记录了每一块虚拟地址与物理地址的映射关系。偷鸡的关键就在这里。进程a，将数据存在虚拟内存 0 中。进程b，存在地址一，此时页表被内核篡改， a 的虚拟内存实际指向了 b 的物理地址。在进程 a 看来，它并不知道数据实际流向，也没有违反隔离规则，但实际上数据已经跨越了进程，被拷贝到了进程 b 的空间。整个过程，进程 a 完全蒙在鼓里， Lydic 称之为临时映射数据进了门之后改个门牌号，临时映射在没有违反规则的前提下，绕过了陷入内核这一步，减少了单次 IPC 的时间开销。
论文提出的 18 条优化中， 17 条都在做这件事。 Lydic 将微内核从架构到算法通通优化，改动之大无异于重构。他在 2001 年去世前仍以每年一篇的速度发表着论文，而他研发的 L4 微内核系统如今在 10 亿多手机的通信芯片中悄然运行。这些工作都在试图证明同一件事，微内核的低效并非固有缺陷。微内核的故事充满了好点子和死胡同。 Latteck 在通向真正微内核论文的第一句话如此说道。而鸿蒙这篇名为微内核走向通用的论文仿佛是一次接力，让我们回到这篇论文，鸿蒙虽然仍在解决 IPC 的耗时问题，但并没有像 Latteck 一样只关注 IPC 本身，而是将目光投向了更本质的问题权限用户态进程之所以要在内核中转，是因为权限不够，需要通过高权限的内核才能通信。
鸿蒙的思路是那干脆在用户态与内核态中间再造一层，一共三种态， SA 2、SA1、SA0，权限依次增大，最小的 SA 2 和最大的 SA0 就是以前的用户态和内核态。其中 SA1 最特殊，它里面的进程彼此地址隔离，但是又有权像内核态一样执行特权指令。 IPC 无需再通过内核。鸿蒙将文件系统和内存管理这些对性能影响最大的服务放入了SA1，通信开销相比用户态减少了50%。
除此之外， SA1 中的地址还可以根据需要共享。比如在车机系统中要同时控制多种硬件，开发者可以将这些硬件的驱动服务的地址合并到一块，彼此间访问无障碍，系统响应就更迅速。这还不够，还有个做法更加激进，鸿蒙直接将权限授予给部分进程，他们不用再经过内核同意，就能访问内核中特定对象，这打破了传统需要经内核校验的规则。传统内核授权的耗时很久，这么做就将授权加访问或撤销的逻辑分为访问不能访问两步划一步，耗时降低了两个数量级，就像宿管阿姨给你开了找女朋友的小窗户，这是在安全与性能间做了更细致的工程权衡。一系列设计将微内核再次重构，让系统更灵活的部署到各类硬件终端，这应该就是论文标题中走向通用的愿景。
这些架构设计看上去并不复杂，华为投入了近 10 年，但对于一款操作系统来讲，开发成功仅仅是开始。这是一张维基百科页面，上面列举了一共 189 种操作系统，他们有一个共同点，如今都已停产，其中的 159 种都集中在波士顿 128 号公路沿线以及旧金山湾区。那是个人电脑的黄金时代， 80 年代的硬件厂商几乎都会独立研发操作系统，但随着 90 年代 PC 市场的激烈竞争，主流操作系统只剩下三家，这一格局奠定至今。今那些被淘汰的系统们，并非是技术不行，而是技术只是入场券。
一款操作系统要真正可用，需要上下游的通力配合，厂商要生产与其兼容的硬件，开发者要愿意为其编写程序，还要有人编写教材，提供培训，用如今的话来说就是生态， 84 年 Macintosh system one 发布， 85 年 Windows 1.0 发布，网上说微机操作系统的窗口就是 80 年代，而鸿蒙的起跑晚了 40 多年，不过在设计之初，鸿蒙就做好了准备。
鸿蒙内核中的 IC 0 放的不是进程内存，而是兼容 Linux 开发工具的接口。 IC 0 拥有内核三种隔离中的最高权限，这意味着开发者可以利用 Linux 现有的软件生态无缝迁移代码，不用再造轮子。如今的计算设备形态早已不仅是PC，还有手机、平板、手表。每多适配一款设备，开发者就要多搭建一套流程，多设备，统一系统，统一生态。鸿蒙的 openharmony 框架可以让电脑复用手机的生态，实现一次开发、多端部署。一个轮子造好，哪都能跑。 Windows 庞大的兼容体系导致适配困难，例如要实现手机与电脑互联这类新功能，开发者往往要付出双倍成本。鸿蒙的功能师告诉我，减少开发成本对于许多国内的中小开发者来说至关重要。 2025 年，在 PC 黄金时代的 40 年后，我们刚从微内核先驱者们的手中接过接力棒，系统生态还远未完善，微信上线不久，最近刚突破 1, 000 万下载量。但 40 年后回看，这或许是一段历史的新起点，而又一次漫长的接力才刚刚开始。这就是本期视频的全部内容，如果你喜欢，欢迎点赞、投币、转发、关注，我们下期再见。
